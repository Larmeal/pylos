    planner

    pylos.planner ¶

    Resolves a config against reality: which files the glob matches, and a printable plan of the work.

    Plan dataclass ¶

    Plan(engine_id: str, engine_name: str, source: SourceConfig, contract: ContractConfig, on_failure: OnFailureActionConfig, report: SinkConfig, data_docs_enabled: bool, source_objects: list[SourceObjectMetadata])

    What the run will do, resolved against reality, with nothing executed.

    The config alone cannot say which files a run will touch, and the file list alone cannot say what will happen to them. Plan holds both, which is why it is worth rendering before a run instead of after.

    Plan is a plain @dataclass, not a Pydantic model, although every field it holds (source, contract, ...) is a validated Pydantic model. Those models already ran their validators once, when the engine's YAML was loaded. A dataclass never re-runs them, whereas nesting a validated model inside another BaseModel can re-trigger its model_validator\ s unexpectedly. Plan only reads its fields: it is a snapshot, and only a test should construct one by hand.

    ATTRIBUTE DESCRIPTION
    engine_id

    The pipeline's stable id, shown in the header.

    TYPE: str

    engine_name

    Which engine will read the data ("pandas", "spark", "sql").

    TYPE: str

    source

    The declared source, for the pattern, reader and options.

    TYPE: SourceConfig

    contract

    The rules that will be applied to every object.

    TYPE: ContractConfig

    on_failure

    What happens to an object whose critical rules fail.

    TYPE: OnFailureActionConfig

    report

    Where the report is written, whatever the outcome.

    TYPE: SinkConfig

    data_docs_enabled

    Whether GX will also render its HTML view.

    TYPE: bool

    source_objects

    What the glob actually found, sorted by path.

    TYPE: list[SourceObjectMetadata]

    Examples:

    Planner.plan() normally builds it, but a test can construct one directly from fabricated data, without touching a real filesystem:

    >>> plan = Plan(
...     engine_id="test_config",
...     engine_name="pandas",
...     source=source_config,
...     contract=contract_config,
...     on_failure=IgnoreFailureAction(),
...     report=report_config,
...     data_docs_enabled=False,
...     source_objects=[],
... )
>>> print(plan.render())

    ordered_expectations ¶

    ordered_expectations() -> list[ExpectationConfig]

    Every rule, ordered by severity and then by declaration order.

    This is the single definition of rule order. _rule_lines uses it to number --full-rules output, and anything else that needs "rule 4" to mean the same rule every time (a report, a log line) should use it too. It is public, with no leading underscore, so those callers can reuse it instead of re-deriving the order.

    Both sort keys (a rule's severity and its position in self.contract.expectations) come from the config alone, never from anything resolved at plan time. So the order is deterministic: the same contract numbers its rules identically on every run and on every machine.

    RETURNS DESCRIPTION
    list[ExpectationConfig]

    Every expectation in self.contract.expectations, grouped by severity in the order critical, warning, info (_SEVERITY_ORDER), in declaration order within each group. The list is new; the contract's own list is not modified.

    Examples:

    A contract declaring [warning_rule, critical_rule] (in that order) returns [critical_rule, warning_rule]. Severity wins over declaration order, even though critical_rule was written second.

    Note

    To change the severity order (info before warning, say), edit the module-level _SEVERITY_ORDER tuple. Neither this method nor its callers hardcode the three names, so they all follow automatically.

    render ¶

    render(full_objects: bool = False, full_rules: bool = False, full_path: bool = False, timezone: str = 'UTC') -> str

    Renders the plan for a terminal. This is the module's public entry point.

    Everything else in Plan and the module-level helpers supports this method. A caller (a script today, a CLI --dry command later) only needs Planner(engine).plan().render(). It assembles the boxes and the object listing in a fixed order (source, objects, validate, rules, on failure, report, summary). Every argument controls verbosity only. None of them changes what the run would do, only how much of it this call prints.

    PARAMETER DESCRIPTION
    full_objects

    List every resolved object instead of the first five (see _object_lines). For a future CLI --full-objects flag.

    TYPE: bool DEFAULT: False

    full_rules

    List every rule, not just the per-severity counts (see _rule_lines). For a future CLI --full-rules flag.

    TYPE: bool DEFAULT: False

    full_path

    Show each object's path exactly as stored instead of relative to the current directory (see _relative_to_cwd). For a future CLI --full-path flag.

    TYPE: bool DEFAULT: False

    timezone

    IANA zone name to render each object's modified time in, e.g. "Asia/Bangkok". It is the reader's preference, not part of the plan, so it is a render argument instead of a Plan field: the same Plan renders in whatever zone the reader asks for, without being rebuilt.

    TYPE: str DEFAULT: 'UTC'

    RETURNS DESCRIPTION
    str

    The complete plan as one multi-line string, ready to print(). Every line is padded or bordered to a consistent width (see _BOX_WIDTH), so it lines up in a monospace terminal.
    RAISES DESCRIPTION
    ValueError

    timezone is not a recognized IANA zone name (a typo like "Asia/Bangkog", for example). The check runs at the start of the call, before any line is built, so a bad timezone never produces a half-rendered plan.

    Examples:

    >>> print(Planner(engine).plan().render())
  PYLOS plan · test_config · pandas

╭─ source ───────────────────────────────────────────────────────────────────╮
│  storage  : local                                                          │
...
  Plan: 1 object · 9 expectations
    Note

    To add a section (a future runtime box once checkpointing exists, say), write a Plan._runtime_box method like the others and call it here at the right point in the sequence. The existing boxes need no change.

    Planner ¶

    Planner(engine: Engine)

    Turns a declaration into the concrete work a run would do.

    It resolves the source glob, and it is the only part of a dry run that touches the outside world. It only lists: no file is opened, no expectation is run, nothing is moved and nothing is written, so a dry run has no side effect here to switch off.

    Planner (which does the I/O) and Plan (the dataclass above, pure formatting) are separate classes. That lets Plan.render() be tested with fabricated data and no real filesystem, and lets the same resolved Plan be rendered several times (different timezone, full_rules, ...) without globbing again.

    Examples:

    >>> from pylos.loader import from_yaml
>>> engine = from_yaml("data/template_test.yml")
>>> print(Planner(engine).plan().render())
  PYLOS plan · test_config · pandas
...

    Builds a Planner for one engine's declaration.

    PARAMETER DESCRIPTION
    engine

    The loaded, validated pipeline declaration (usually the result of pylos.loader.from_yaml(...)). Planner does not re-read or re-validate it; config mistakes were already caught at load time.

    TYPE: Engine

    Note

    self.backend is pulled out here only so prepare_source_metadata can read self.backend.glob(...) instead of self.engine.source.backend.glob(...). It is the same object as engine.source.backend, not a copy.

    prepare_source_metadata ¶

    prepare_source_metadata() -> list[SourceObjectMetadata]

    Resolves the source's glob pattern against the filesystem, now.

    This is the only I/O in the module; everything else in planner.py formats data that was already fetched. Two calls can return different answers, because a file can appear or disappear in between. That is why Plan is a snapshot: Planner.plan() calls this once, and every part of render() reports against that one list, so the numbers in a printed plan always agree with each other even if the filesystem keeps changing.

    RETURNS DESCRIPTION
    list[SourceObjectMetadata]

    Every object the source's glob pattern matched, as SourceObjectMetadata (path, size, modified time), sorted alphabetically by path. The backend's glob does the sorting, so the plan lists objects in the same order the runner will process them, and the five-object preview in Plan._object_lines is the same on every run.

    Examples:

    For source.file_path: "data/test_*.csv" matching three files, this returns three items sorted as test_1.csv, test_2.csv, test_3.csv, each with its own size_bytes and modified_at timestamp from the filesystem.

    Note

    What "glob" means for local files or a GCS bucket is decided by the storage backend (self.backend.glob, e.g. storages/local.py). This method only calls it, so it works unchanged for every backend that implements StorageBackend.

    plan ¶

    plan() -> Plan

    Resolves the declaration into a Plan. This is the class's main entry point.

    Other code (a future CLI, a test, the examples in this module) calls this method; everything else on Planner and Plan supports it. It does two things: it resolves the source's glob against the filesystem (prepare_source_metadata), and it copies every other field from self.engine unchanged, since those are declared, not discovered.

    RETURNS DESCRIPTION
    Plan

    A Plan combining self.engine's declaration with the result of prepare_source_metadata(). Call .render() on it to get the printable plan.

    Examples:

    >>> plan = Planner(engine).plan()
>>> plan.engine_id
'test_config'
>>> len(plan.source_objects)
1
    Note

    To resolve something else at plan time (checking that the report sink's directory is writable, say), do the work here and pass the result to Plan(...) as another field, the way source_objects is passed. Plan stays a plain snapshot of the result.
