    results

    pylos.results ¶

    The vocabulary of a report: PylosResult and the objects and enums inside it.

    ActionName ¶

    Bases: StrEnum

    What Pylos can do to a source file once on_failure decides to act.

    Mirrors the action field of the on_failure config block one-to-one. The YAML author picks one of these four, and policy.py copies that same value onto the ActionResult it plans, unchanged.

    ATTRIBUTE DESCRIPTION
    IGNORE

    Leave the file exactly where it is. Also the value policy.py uses when nothing needs to happen at all, not only when the user configured it explicitly.
    DELETE

    Remove the file from its source location.
    MOVE

    Relocate the file into dead_letter, removing the original.
    COPY

    Copy the file into dead_letter, leaving the original in place.

    Examples:

    >>> ActionName.MOVE
<ActionName.MOVE: 'move'>

    >>> ActionName.MOVE.value
'move'

    >>> ActionName.MOVE == "move"
True

    ActionStatus ¶

    Bases: StrEnum

    Where one ActionResult is in its own lifecycle, separate from which action it names.

    policy.py only ever produces PENDING or SKIPPED. The runner moves a PENDING row to COMPLETED or FAILED once it has tried to perform the action.

    A row still at PENDING in a written report means the process died between planning the action and carrying it out.

    ATTRIBUTE DESCRIPTION
    PENDING

    The action is due but has not run yet.
    SKIPPED

    Nothing needs to touch the file, e.g. the decision was PASSED or WARNED.
    COMPLETED

    The runner performed the action and it succeeded.
    FAILED

    The runner tried to perform the action and it raised.

    Examples:

    >>> ActionStatus.PENDING
<ActionStatus.PENDING: 'pending'>

    >>> ActionStatus.PENDING == "pending"
True

    Decision ¶

    Bases: StrEnum

    Was the data itself good, for one source object or for the whole run.

    Derived from expectation severities, not from whether Pylos managed to run at all. An object that could not be read has no Decision, because there was no data to judge (see RunObjectStatus.ABORTED).

    ATTRIBUTE DESCRIPTION
    PASSED

    No expectation failed, or only info ones did.
    WARNED

    The worst failing expectation was warning.
    FAILED

    At least one critical expectation failed.

    Only FAILED ever triggers the configured on_failure action. The other two leave the file untouched but are still written to the report.

    At the run level, PylosResult.decision rolls these up across every object. It answers "is the data okay" for whoever owns the data. RunStatus answers a different question, "did Pylos do its job", for whoever runs the pipeline.

    Examples:

    >>> Decision.FAILED
<Decision.FAILED: 'failed'>

    >>> Decision.FAILED == "failed"
True

    RunStatus ¶

    Bases: StrEnum

    Did Pylos manage to do its job for this run, independent of what the data looked like.

    A rollup of every object's RunObjectStatus, not of their Decision. A run where every single file failed every expectation is still COMPLETED, because Pylos read and validated all of them successfully.

    ATTRIBUTE DESCRIPTION
    COMPLETED

    Every object completed, including an empty, allowed glob.
    PARTIAL

    A mix of completed and aborted objects.
    ABORTED

    Every object aborted.

    ABORTED should draw attention before PARTIAL. When no object could even be processed, the cause is usually systemic (bad credentials, a network outage), not ordinary bad data.

    PARTIAL is the everyday case of "partial failure continues": a few files could not be read, and the rest still ran.

    Read by whoever runs the pipeline; Decision is read by whoever owns the data.

    Examples:

    >>> RunStatus.PARTIAL
<RunStatus.PARTIAL: 'partial'>

    >>> RunStatus.PARTIAL == "partial"
True

    RunObjectStatus ¶

    Bases: StrEnum

    Did Pylos finish processing one source object, independent of the verdict.

    Set once per object, before Decision is even known.

    ATTRIBUTE DESCRIPTION
    COMPLETED

    The object was read and every expectation ran, whatever the result was.
    ABORTED

    Something raised before that point instead, e.g. a corrupt file or an unreadable encoding, caught by the runner's try/except around the read and validate steps.

    RunStatus is the rollup of these two values across every object in the run.

    Examples:

    >>> RunObjectStatus.ABORTED
<RunObjectStatus.ABORTED: 'aborted'>

    >>> RunObjectStatus.ABORTED == "aborted"
True

    Severity ¶

    Bases: StrEnum

    Pylos's own mirror of GX's FailureSeverity: same three levels, no GX import.

    Building a GX expectation suite requires a FailureSeverity value (from great_expectations.expectations.metadata_types). results.py is a leaf module that imports nothing from Pylos or GX, so every other module can depend on it without pulling in great_expectations.

    An equivalent enum here keeps that boundary. gx/validator.py's _map_severity is the only place that translates between the two.

    ATTRIBUTE DESCRIPTION
    CRITICAL

    A failure triggers the configured on_failure action.
    WARNING

    A failure is recorded but the file is left alone.
    INFO

    A failure is recorded as a note for a person, nothing more.

    Examples:

    >>> Severity.CRITICAL
<Severity.CRITICAL: 'critical'>

    >>> Severity.CRITICAL == "critical"
True

    SourceObjectMetadata pydantic-model ¶

    Bases: BaseModel

    Resolved reality for one source object: where it is, how big, how old.

    Produced by storage.glob. Every backend fills the same four required fields from its own listing, so a missing one fails at construction instead of showing up as a hole in the report. created_at is always present, but it is exact only where the backend reports a creation time; elsewhere it is an approximation (see the field). metadata is a backend-specific bag that nothing downstream interprets.

    Fields:

    • path (str)
    • size_bytes (int)
    • created_at (datetime)
    • modified_at (datetime)
    • metadata (dict[str, Any])

    path pydantic-field ¶

    path: str

    Full URI of the source object, the report's source_object key.

    size_bytes pydantic-field ¶

    size_bytes: int

    Object size in bytes, from the listing.

    created_at pydantic-field ¶

    created_at: datetime

    Creation time (UTC), from the listing. Exact where the backend reports it (GCS, Windows, macOS). An approximation otherwise: on Linux, Python's os.stat does not expose the creation time, so a backend that cannot tell falls back to modified_at.

    modified_at pydantic-field ¶

    modified_at: datetime

    Last-modified time (UTC), from the listing.

    metadata pydantic-field ¶

    metadata: dict[str, Any]

    Backend-specific extras nothing downstream interprets (e.g. GCS etag, md5_hash).

    ExpectationResult pydantic-model ¶

    Bases: BaseModel

    The outcome of one expectation against one source object: one row in the report.

    Filled by gx/ and never changed afterwards. The fields lifted out of GX's nested dicts are the ones code outside gx/ reads: severity and success drive the policy decision, and the rest become report columns. exception_message is kept apart from success because a rule GX could not run did not pass.

    • observed_value (Any | None)
    • unexpected_count (int | None)
    • unexpected_percent (float | None)
    • unexpected_values (list[Any] | None)
    • unexpected_index (list[int] | None)
    • raised_exception (bool)
    • exception_message (str | None)
    • meta (dict[str, Any])
    • notes (str | None)

    success pydantic-field ¶

    success: bool

    Indicates whether the expectation was met.

    expectation_name: str | None = None

    expectation_type pydantic-field ¶

    expectation_type: str

    The type of the expectation that was checked.

    expectation_key pydantic-field ¶

    expectation_key: str

    The unique key identifying the expectation that was checked.

    expectation_kwargs pydantic-field ¶

    expectation_kwargs: dict[str, Any]

    The keyword arguments passed to the expectation (e.g., {'column': 'id'}).

    description pydantic-field ¶

    description: str | None = None

    notes: str | None = None

    Additional notes about the expectation result, if applicable.

    ActionResult pydantic-model ¶

    Bases: BaseModel

    What was done to the source object, and whether it worked.

    Written twice. status is pending when the report records the intent; once the action has run, the same instance is updated and the report is merged onto the same row. A row left at pending means the process died between the two writes. That is why this model is mutable.

    Fields:

    • action (ActionName)
    • status (ActionStatus)
    • dead_letter (str | None)
    • error (str | None)

    action pydantic-field ¶

    action: ActionName

    The name of the action that was taken.

    status pydantic-field ¶

    status: ActionStatus

    Indicates the status of the action.

    dead_letter pydantic-field ¶

    dead_letter: str | None = None

    The directory path where the file should be moved/copied or where metadata should be saved.

    error pydantic-field ¶

    error: str | None = None

    Error message if the action failed.

    SourceObjectResult pydantic-model ¶

    Bases: BaseModel

    Everything that happened to one source object.

    Its fields come from different steps of the run: the planner supplies source_object, the reader the counts and timings, gx/ the expectations, the policy the decision, and the action its outcome. Many fields are optional because a step may never run: an object that could not be read has no row_count and no expectations, but it still has to be recorded and dead-lettered.

    Fields:

    • status (RunObjectStatus)
    • source_object (SourceObjectMetadata)
    • row_count (int | None)
    • column_count (int | None)
    • read_duration_sec (float | None)
    • validation_duration_sec (float | None)
    • error_type (str | None)
    • error_message (str | None)
    • decision (Decision | None)
    • expectations (list[ExpectationResult] | None)
    • action (ActionResult | None)
    • raw_gx_result (dict | None)

    status pydantic-field ¶

    status: RunObjectStatus

    The status of the validation operation.

    source_object pydantic-field ¶

    source_object: SourceObjectMetadata

    The identifier or name of the source object being validated.

    row_count pydantic-field ¶

    row_count: int | None

    The number of rows processed during the validation operation.

    column_count pydantic-field ¶

    column_count: int | None

    The number of columns processed during the validation operation.

    read_duration_sec pydantic-field ¶

    read_duration_sec: float | None = None

    The duration of the read operation in seconds.

    validation_duration_sec pydantic-field ¶

    validation_duration_sec: float | None

    The duration of the validation operation in seconds.

    error_type pydantic-field ¶

    error_type: str | None

    The type of error that occurred during the validation operation, if any.

    error_message pydantic-field ¶

    error_message: str | None

    The error message associated with the error that occurred during the validation operation, if any.

    decision pydantic-field ¶

    decision: Decision | None

    The decision made based on the validation results, if any.

    expectations pydantic-field ¶

    expectations: list[ExpectationResult] | None

    The list of expectation results for the source object.

    action pydantic-field ¶

    action: ActionResult | None

    The result of the action taken after the validation operation, if any.

    raw_gx_result pydantic-field ¶

    raw_gx_result: dict | None

    The raw result from the GX operation, if any.

    PylosResult pydantic-model ¶

    Bases: BaseModel

    The result of one run: what the library returns and what the sinks write.

    It carries what a CLI exit code cannot: which objects were checked, what was decided about each, and what was done to them. The run-level verdicts are summaries of results; nothing else decides them.

    Fields:

    • pylos_version (str)
    • run_id (str)
    • run_ts (datetime)
    • results (list[SourceObjectResult])
    • run_status (RunStatus)
    • decision (Decision | None)

    pylos_version pydantic-field ¶

    pylos_version: str = _PYLOS_VERSION

    The version of Pylos used for the validation.

    run_id pydantic-field ¶

    run_id: str

    The unique identifier for the specific run of the Pylos operation.

    run_ts pydantic-field ¶

    run_ts: datetime

    The timestamp of the specific run of the Pylos operation.

    results pydantic-field ¶

    results: list[SourceObjectResult]

    One entry per source object the planner resolved. Every planned object ends up here whether it validated or aborted, so an empty list means the glob matched nothing.

    run_status pydantic-field ¶

    run_status: RunStatus

    Did Pylos manage to do its job: a rollup of results[].status, which is only 'completed' or 'aborted' per object. Empty results: 'completed', because the glob matched nothing and source.on_empty allowed it. All completed: 'completed'. All aborted: 'aborted', which is systemic and should be louder than 'partial'. Otherwise 'partial'. Answers a different question from data_decision: this one is read by whoever runs the pipeline, that one by whoever owns the data.

    decision pydantic-field ¶

    decision: Decision | None

    The overall data decision based on the validation results, if any.
